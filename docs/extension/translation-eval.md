# 翻译质量评测

改翻译提示词、模型或参数之前和之后，用同一批样本对比译文，避免凭感觉判断。只在开发时运行，不进扩展安装包，也不在 `npm test` 里跑（要调用真实接口）。

## 组成

| 文件 | 作用 |
| --- | --- |
| `apps/extension/eval/samples.json` | 样本：日文、英文原文各 30 条，中文原文 20 条，覆盖新闻、论坛口语、技术文档、随笔、电商和界面短句；原文与目标是同一种语言的样本自动跳过 |
| `apps/extension/eval/variants.mjs` | 待对比的方案，每个方案只描述在线上请求体基础上改什么 |
| `apps/extension/eval/run.mjs` | 翻译、盲评、生成报告 |
| `apps/extension/eval/sense.mjs`、`sense-candidates.json` | 义项提示筛选：按候选词自动写样本、测现版、加提示对比，见下文「义项提示筛选」 |

脚本加载扩展自己的 `src/lib/providers.js`，照常调用 `translate`（整段）和 `translateBatch`（网页片段），发出请求前把请求体交给方案的 `patch`。因此 `baseline` 始终是当前代码的真实行为，改了提示词不需要同步评测代码。

## 运行

需要 `DEEPSEEK_API_KEY`，查找顺序与界面译文生成器相同（`apps/extension/.env.local`、根目录 `.env.local`、进程环境）。

```sh
npm run eval:translation -- --list
npm run eval:translation -- --variants baseline,temp-0.7
npm run eval:translation -- --variants baseline,temp-0.7 --from ja --genre forum,essay
npm run eval:translation -- --variants baseline --no-judge
npm run eval:translation -- --variants no-style,baseline --target en
```

`--variants` 的第一个是对照组，其余每个都和它两两比较。其他选项见 `--help`。

报告写到 `dist/eval/<时间>-<方案>/report.md`（另有 `results.json`）：先是各方案实际发出的参数，然后是按源语言、体裁、整段或片段分组的胜 / 平 / 负与两项平均分，最后是逐条译文和评审理由。

相同的请求会复用 `dist/eval/cache.json` 里的结果，重跑不花钱，对照组的译文也保持不变；要重新请求加 `--fresh`（只是不读缓存，新结果照常写回）。DeepSeek 默认温度 1.3，同一请求每次结果不同，比较两个方案时不要中途清缓存。

## 评审方式

评审模型拿到原文和两份译文（A、B 顺序按样本固定打乱，不知道哪份来自哪个方案），分别给「忠实」和「地道」打 1–5 分，再判断整体哪份更好；意思有明显错误的一份不能赢，差不多就判平。两份译文完全相同时不调用评审，直接记平。

默认评审模型是 `deepseek-flash`（开启思考）。不使用 `deepseek-v4-pro`，无论是做翻译方案还是做评审。可用 `JUDGE_MODEL`、`JUDGE_BASE_URL`、`JUDGE_API_KEY` 换成任何 OpenAI 兼容接口。

## 读结果时要注意

- 评审与被评的模型同属 DeepSeek，可能偏好自己习惯的说法，打分也偏宽松。条件允许时换一家的模型做评审。
- 60 条样本下，胜负差几条属于噪声。看胜负是否明显偏向一边、各分组方向是否一致，再读逐条译文确认。
- 「忠实度下降的样本」要人工复核：更顺口但意思走样的译文不算改进。
- 样本的 `watch` 字段是写给人看的提示（这条容易在哪里生硬），不会发给评审。

## 义项提示筛选

`npm run eval:sense` 把找义项提示的流程自动化，落地仍由人决定：

1. 候选写在 `apps/extension/eval/sense-candidates.json`，一行一个词：

   ```json
   { "id": "ja-tegami", "from": "ja", "word": "手紙", "sense": "信、书信", "trap": "手纸" }
   ```

   `sense` 是容易译错的义项，`trap` 是照字面会译成的错误意思。可选字段：`pattern`（正则；日语默认按 `word` 字面匹配，如 `(?<!大)丈夫`；英语默认整词、不分大小写，变形要写进来，如 `sanction(?:s|ed|ing)?`）、`negative`（照字面译本来就对的义项，会另写 2 条反例）、`hint`（不写就按模板生成）。
2. 由 `deepseek-flash` 为每个候选写 4 条整段正例、1 组网页片段，有 `negative` 的另写 2 条反例。不含该词的样本丢掉。
3. 调 `run.mjs` 用现版翻译（`baseline`），再请评审只判断这个词译对没有。
4. 现版在正例里错 2 条及以上（`--min-errors`）的候选，用 `sense-candidate` 方案加上这一条提示重翻，整句盲评，再判一次词义。
5. 报告写到 `dist/eval/sense/<时间>/report.md`：每个候选一行结论，「建议落地」附可直接粘贴进 `senseHints` 的代码行，后面是逐条译文与判断理由。

结论的含义：

| 结论 | 条件 |
| --- | --- |
| 不需要 | 现版在正例里错得少于 `--min-errors` 条，不试提示 |
| 建议落地 | 加提示后正例最多错 1 条且比现版少，反例没有变差，整句盲评负不多于胜 |
| 有副作用 | 反例变差，或整句盲评负多于胜 |
| 无效 | 提示没能把正例改对 |

样本生成、词义判断（`dist/eval/sense-cache.json`）与翻译、盲评（`dist/eval/cache.json`）都带缓存，重跑不花钱。改了候选的 `hint` 只会重新请求加提示的那一步。生成的样本在报告目录的 `samples.json` 里；决定落地的词，把正反例挑进 `sense-samples.json`，便于以后用 `no-sense` 回看。

现版本来就译对的词不要加提示：试跑时给「微妙」硬加提示，整句盲评 1 胜 2 平 4 负，反例也错了一条。

### 第一轮：日语同形异义词（2026-11-24）

`sense-candidates.json` 收了 42 个日中同形异义词（手紙、勉強、検討、大丈夫、高校、経理等），共生成 218 条样本，用自带 Key 路径的 `deepseek-flash` 翻译。

- 39 个现版正例错不到 2 条，结论「不需要」。其中 35 个一条没错，手紙、検討、勉強、留守、汽車、階段这类常被举例的词，现版都能按语境译对。另在现版译文里按字面搜了一遍错误译法，没有发现判断器漏掉的错译。
- 大家（房东）：现版 5 条正例错 2 条（「大家要换地方」「向各位确认」），加提示后全对；两条「日本画の大家」类反例不受影响；整句盲评 4 胜 1 平 2 负。已落地（见下）。
- 告訴：现版把它译成「起诉」「提起诉讼」，按这个错处改写提示后正例改对，但整句盲评 2 胜 3 负，判断器对「报案」也前后不一，结论「有副作用」。只出现在法律语境，暂不收。
- 是非：判断器把「请尽早购买」这类没写「务必」的译法算作错。加提示后译文变生硬（2 胜 2 平 3 负），结论「有副作用」，这与人工判断一致。

经验：`trap` 要写现版实际会译成的错误说法，不要只写字形相同的中文词，否则提示打不中错处（告訴 第一版提示写的是「不是告知义的告诉」，模型反而照抄出「报案（告诉）」）。词义判断与盲评都是单次 `deepseek-flash`，「建议落地」的词仍要逐条读译文。

落地「大家」时做了两处调整：

- `senseHints` 只看含假名的段落。大家 在中文里也是常用词，繁体中文原文（如「大家好」）译成简体时不能提示“房东”。判断逐段进行，批量翻译时中文段落不会因为同批有日文段落而带上提示，每段的缓存键也只受它自己命中的提示影响。代价是单独成段、没有假名的「大家」（如被链接切出来的一段）不加提示。撥水、来年度两条的评测样本都含假名，不受影响。
- 正则写成 `/大家(?!族)/`，不让「大家族」命中。

六条正反例与一组网页片段收进 `sense-samples.json`（`ja-sense-13` 到 `ja-sense-19`）。自带 Key 路径落地后的请求与筛选时逐字相同（全部命中缓存）。另补测托管提示词：不加提示时 4 条整段正例错 3 条（「大家要换地方」「向各方确认」「威胁被害人」），加提示后全对，整句盲评 3 胜 2 平 2 负，负的两条只是措辞差别，反例不受影响。

```sh
npm run eval:translation -- --variants no-sense,baseline --samples apps/extension/eval/sense-samples.json --ids ja-sense-13,ja-sense-14,ja-sense-15,ja-sense-16,ja-sense-17,ja-sense-18,ja-sense-19
```

### 第二轮：英语易错词（2026-11-24）

同一份清单加了 36 个英语候选（`from: "en"`，用 `--from en` 单独跑）：一词多义（sanction 批准、moot 已无意义、outstanding 未付、appreciate 升值、tender 投标、fixture 赛程、stock 高汤等）、形容词与名词同形（minute、content、novel、sound）、英美用法差别（public school、grade、table、trunk）。英语默认整词、不分大小写匹配，变形写进 `pattern`；判词义用不举日语例子的那份提示。

- 34 个现版正例错不到 2 条，结论「不需要」，其中 29 个一条没错。错 1 条的（patronize、sensible、bill、meaningful 等）多是漏译修饰语或可接受的说法。
- public school：现版把英国语境（牛津、萨里、口音、学费昂贵）里的 5 条全部译成「公立学校」，意思正好相反。第一版提示把美国语境的反例也改成了「私立公学」（反例 0 → 2，有副作用）；改成「有英国线索时译公学或私立公学，美国等语境或看不出国别时照常译公立学校」后，筛选里正例全对，反例不变，整句盲评 6 胜 1 负，结论「建议落地」。落地前的复测见下。
- novel（新颖的）：现版只有漏译，加提示后模型写成「新奇的想法」，整句盲评 2 胜 1 平 4 负，结论「有副作用」。

落地 public school 时的复测与调整：

- 托管提示词上，上面那版提示正例 5 条全对，但把美国语境的「local public school」和看不出国别的「Our public school just got new laptops」也译成了「公学」。另写 10 条美国或看不出国别的反例，连同原有 2 条共 12 条，托管路径错 2 条。网页上美国用法远多于英国用法，这个比例不能接受。
- 改成先说默认：「public school 默认照常译作“公立学校”；只有上下文明确是英国（伊顿、牛津剑桥、英国地名、学费昂贵、口音等线索）时，才是收费的私立公学，译作“公学”或“私立公学”。」两条路径上 12 条反例全部保持「公立学校」，5 条英国正例改对 3 条（牛津、口音、祖父那句）；「a public school in Surrey」和只说学费比房贷贵的那句仍译成公立学校。整句盲评自带 Key 6 胜 9 平 2 负、托管 7 胜 8 平 2 负，负的几条都是重新采样的措辞差别。按这一版落地。
- `senseHints` 的每条改为标明源语言：日语条目仍要求段落含假名，英语条目按整词、不分大小写匹配，不要求假名。
- 正反例收进 `sense-samples.json`（`en-sense-07` 到 `en-sense-13`）。只改提示词时可以先在两条路径上用 `--no-judge` 数反例里出现「公学」的次数，再跑盲评。

## 添加样本

样本都是为评测自行撰写的，不摘抄真实网页。遇到实际使用中翻得生硬的句子，改写后加进 `samples.json`：

```json
{ "id": "ja-forum-07", "from": "ja", "genre": "forum", "text": "…", "watch": "容易出问题的地方" }
{ "id": "en-batch-05", "from": "en", "genre": "ui", "mode": "batch", "texts": ["…", "…"], "watch": "…" }
```

`mode: "batch"` 模拟网页翻译：`texts` 是一个页面上相邻的文本片段，可以包含被行内标签切开的半句话。

## 添加方案

在 `variants.mjs` 里加一项。改参数直接返回新的请求体；改系统提示词用 `withSystem`，`ctx.mode` 区分整段与片段，`ctx.target` 是目标语言的英文名：

```js
'zh-style': {
  note: '加中文风格指南',
  patch: withSystem((prompt, ctx) => (ctx.target.includes('Chinese') ? `${prompt}\n…` : prompt)),
},
```

要在初译之后再做一步（如审校改写），给方案加 `after({ mode, sample, target, output, call })`，`call(body)` 用同一个带缓存的接口再发一次请求，返回值作为最终译文（报告的 `results.json` 里另存初译 `draft`）。

温度 1.3 下同一方案每次结果不同。判断差距是否超出波动，可以加一个只在提示词末尾多一个换行的「重新采样」方案（如 `baseline-resample`）一起跑：2026-11 的一轮里 `baseline-resample` 对 `baseline` 是 14 / 25 / 21，胜负差在这个范围内的候选不能算改进。

方案验证有效后，再把改动落到 `src/lib/providers.js` 和后台 `src/translation/hosted.js`（两边保持一致），然后删掉对应的方案。
