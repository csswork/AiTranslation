# 响应速度跟踪

目的：按地域、人群和使用场景找出托管翻译慢在哪一段，决定改进方向。只记录毫秒数和固定取值，不含原文、译文或网址。

## 记录了什么

每条托管文字请求（`usage_events`，迁移 `015_latency_breakdown.sql`）：

| 列 | 含义 |
| --- | --- |
| `precheck_ms` | 收到请求 → 开始调用模型：鉴权、订阅与额度检查、预扣点数 |
| `latency_ms` | 模型调用本身（含主力失败后改用备用的那次）；缓存命中时接近 0 |
| `ttft_ms` | 收到请求 → 发出第一段译文，仅流式请求 |
| `server_ms` | 收到请求 → 响应就绪（含模型返回后的余额查询，不含最后写这条记录） |
| `stream` | 是否流式返回 |
| `ext_version` | 扩展版本（请求头 `X-Huaci-Version`，迁移 016）；旧版扩展不带时为空 |
| `surface` | 扩展里的使用场景：`selection` 划词弹窗、`panel` 翻译面板、`page` 网页元素、`site` 整站、`image` 图片、`pdf`、`reader` 双语阅读、`subtitle` 视频字幕；旧版扩展不传时为空 |

已有的 `country`（需设置 `GEO_COUNTRY_HEADER`）、`audience`（访客、注册、订阅）、`chars`、`provider`、`error = 'primary_failed'`（改用备用）一起用于分组。

`server_ms` 是服务端视角，不含客户端到 VPS 的网络往返；客户端实测（第 2 阶段）随扩展后续版本加入。

## 在哪看

管理端「运营概览 → 性能与异常 → 响应速度」：按国家、人群、场景、扩展版本各一张表，列出总耗时与首字的 P50/P90、准备 P50、模型 P50/P90，以及改用备用、缓存命中与失败的比例。少于 20 条的分组不显示百分位。迁移之前的请求只有模型耗时，所以模型列可以直接当作基线。

## 怎么读

- 总耗时高、模型耗时也高：模型或模型服务商所在地的问题，看「改用备用」比例和按目标语言、字数的差异。
- 总耗时明显高于准备 + 模型：模型返回后的处理变慢（数据库）。
- 准备 P50 上升：数据库查询变慢，优先看订阅用户（每次请求会汇总本月字数）。
- 同一场景下不同国家的服务端耗时接近，但用户仍反馈慢：瓶颈在网络往返，需要客户端实测确认后再考虑多地部署。
- 比较人群时先固定场景和字数段，人群间的差异往往来自使用场景构成不同。
